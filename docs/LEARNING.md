# 从前端转到 Flutter 视频播放，按成果推进

你已经会前端，不必重新从变量、循环学起。先把“点击播放”在 Flutter、插件、系统播放器之间的调用讲清楚，再逐个补齐 JD。读完文档不等于精通；每一步都应留下可复现的操作、代码和测试记录。

本工程已经提供第 1～4 步的练习代码。真机验收、接入现有 douyin、服务端和进阶模块仍需继续完成。

## 第 1 步：读懂 Flutter 页面，不只会写 WebView 壳

**目标：** 能独立改首页、内容卡片、播放器控制区和返回行为。

沿着 `main.dart` 读一次：

1. `main()` 启动 `AssetServer`，素材保留在手机应用进程中。
2. `VideoLabApp` 创建 MaterialApp，设置主题和首页。
3. 点击卡片，`Navigator.push` 打开 `PlayerPage`，传入初始模式和同一个演示身份状态。
4. `PlayerPage.initState` 注册生命周期监听、建立 `PlaybackSession`。
5. 首帧回调后初始化播放器，避免在 Widget 正在构建时触发状态更新。

对照已有前端经验：

- Widget 是 UI 的描述；`build` 可能频繁执行，不应在里面创建播放器或发起请求。
- `State` 保存页面生命周期内的数据。`setState` 请求重建 UI，不是“立即重新执行页面全部副作用”。
- `ChangeNotifier` 是这里的状态通知器，类似一个有订阅能力的轻量 store。业务切换规则在 `PlaybackSession`，按钮负责发命令。
- `Future` 表示异步结果，类似 Promise；`await` 不会自动取消任务。
- `dispose` 是释放入口，但它不能被声明成异步来让 Flutter 等待。需要等待的退出流程在 `leave → session.close` 中完成。
- `mounted` 只说明 Widget 仍在树上，不代表异步结果仍属于当前视频。当前工程通过单一会话和忙碌锁阻止并发切换。

**动手：** 在首页添加第三张“异常排查”卡片，进入只展示测试步骤的普通 Flutter 页面。复用卡片组件，不复制整个首页。

**验收：** 小屏不溢出、能返回、没有在 build 中初始化资源。讲清楚路由参数在哪里传递。

**面试自检：** “React useEffect 的清理与 Flutter dispose 有哪些相似点？为什么 mounted 不能替代请求版本检查？”

## 第 2 步：跟踪一次第 8 秒接力

**目标：** 能解释播放位置、播放意图和实际播放器状态为什么需要区分。

假设原生视频在 8.0 秒、1.5 倍速、静音，用户点“交给 H5”：

1. `PlayerPage` 调用 `session.switchTo(PlayerMode.h5)`。
2. 会话进入 busy，UI 禁止重复操作。
3. `NativeEngine.freeze` 记住之前是否在播放，暂停后读取最新位置，返回快照。
4. 会话释放原生播放器，把快照存在 `checkpoint`。
5. 创建 `H5Engine`，通知 Widget 树挂载 WebView。
6. H5 的 video 元信息可用后发 `ready`；Flutter 发送 `restore`，恢复位置、倍速和静音，暂不播放。
7. 只有页面未退出、App 仍在前台且途中没有发生后台暂停，才按原来的播放意图执行 `play`。
8. 结束 busy。H5 后续状态事件更新界面。

“之前在播放”是用户意图；旧播放器已经被暂停，是实际状态。若把两者混在同一个布尔值里，接力后可能永远暂停，或者退到后台后又自动播放。

**失败回退：**

- 旧播放器暂停未确认：保留旧播放器，显示错误，不创建第二个播放器。
- 新播放器初始化失败：销毁失败实例，保留进度，重试时先停在暂停状态。
- 初始化期间关闭页面：等待这一轮结束后释放，禁止执行迟到的 play。
- 一条控制命令还没完成：先禁止切换，避免播放命令和释放资源交错。

**动手：** 阅读 `playback_test.dart`，把“目标初始化失败”测试里的 position 改为 12.5。确认重试保留的是 12.5，而不是硬编码的第 8 秒。

**验收：** 能在日志中说明为什么新播放器创建一定晚于旧播放器停止。真机连续切换时只有一路声音。

**面试自检：** “切换视频后，上一条请求晚回来怎么办？用 mounted 判断够不够？”

## 第 3 步：练会 JSBridge 的成功与失败

**目标：** 不把 evaluateJavaScript 当成“随便执行一段字符串”。

Bridge 是 App 与网页约定的消息接口。这里 Flutter 用 JSChannel 接收网页消息；发送时先 jsonEncode，再调用固定的 `window.receiveFromHost`。不拼接用户输入成为 JavaScript 代码。

阅读 [协议](BRIDGE.md)，重点看三种标识：

- `v`：协议版本，双方是否理解同一套字段。
- `session`：这一份 H5 页面的会话，防止上一个 WebView 的消息混进来。它不是登录凭证。
- `id`：一次命令的请求编号，把响应交给正确的等待者。

**动手：** 增加一个“回到第 5 秒”的命令。先写一个未知方法被拒绝的测试，再实现固定方法、有限数字校验、进度上限、成功响应和失败响应。不要实现通用 `eval` 命令。

**验收：** 非法数字被拒绝；过期 session 无效；响应超时不会无限转圈；页面释放后等待中的请求能结束。

**面试自检：** “JSBridge 的回调丢了怎么办？重复响应怎么办？为什么不能把网页传来的 origin 当成鉴权依据？”

## 第 4 步：跑通两端兼容性

**目标：** 把“理论可用”变成可复现的设备记录。

先完成 [设备运行指南](DEVICE-SETUP.md)。至少测试一台 Android 和一台 iPhone，再补模拟器。记录实际设备，不写“兼容所有 Android/iOS”。

需要分开判断：

- 页面全屏：Flutter 隐藏导航和系统 UI，调整布局。
- 方向请求：请求系统横屏；系统可能不接受。
- H5 video 全屏：WebView/系统视频控件接管，行为与 Flutter 页面全屏不同。
- App 生命周期：失去前台时暂停；不是所有 inactive 都表示用户彻底退出。
- 路由生命周期：切到另一页时是否仍播放。当前播放器页只提供首页退出和同页切换；以后增加详情路由，需要补充路由可见性处理。

**动手：** 按设备验收清单执行，保存一份失败记录。即使最后都正常，也保留测试版本、步骤和结果。

**验收：** 能说明一个真实问题如何定位到页面、Bridge、播放器插件、系统策略或素材，而不是只写“兼容性优化”。

## 第 5 步：接入你自己的 douyin H5

**目标：** 复用现有前端能力，形成一个真正的混合项目。

当前没有读取到 douyin 源码。拿到代码后，先定位“当前激活视频是谁”和“video 引用在哪里”，不要直接把整个站点 URL 填进 WebView 就结束。

建议先接一条视频详情页：

1. 把直接操作 video 的位置收敛到一个适配模块。
2. 实现本工程的 ready、restore、play、pause、freeze、state、handoff 协议。
3. 冻结时暂停当前真正发声的视频，不能只修改 Vue/React store。
4. H5 资源部署在自己控制的 HTTPS 域名，宿主只允许精确的协议、主机、端口和指定入口路径。
5. 保留本地练习页作为对照页。远程页失败时，先判断是网络、域名限制还是 Bridge，不要同时重写两端。
6. 接通详情页后，再接上下滑短视频流。离屏视频必须暂停，旧请求不得更新新卡片。

**验收：** Flutter 与 douyin 在同一 videoId 上接力，进入另一条视频不会沿用上一条的进度。视频 ID、媒体版本和进度应一起传递。

当前协议仅使用同一个测试视频，所以尚未加入 videoId；接入多视频时，这个字段必须补上并参与响应校验。

## 第 6 步：补真实服务和用户状态

**目标：** 覆盖 JD 的后端、CMS、用户和埋点对接。

先约定三个真实接口，再实现 UI：

- 视频详情：videoId、内容状态、播放源、清晰度、字幕、封面和权限结果。
- 播放凭证：服务端检查登录、地区和会员，返回短时播放凭证或受控 URL。
- 观看进度：按用户、视频和媒体版本保存位置，并定义多设备覆盖规则。

演示身份只能证明字符串在两端同步，不能当作登录系统。生产接入时，不把长期 Token 放 URL、日志或任意网页；App 与 H5 要明确 Cookie/令牌各自由谁管理，退出登录要清理本地状态和旧异步结果。

**动手：** 先做 mock 接口，再接真实服务。模拟详情成功但凭证过期、接口超时、退出登录后旧响应晚到三种场景。

**验收：** 能复现 401/403/资源过期的不同 UI 行为；重试有上限；不把前端隐藏按钮当作会员鉴权。

**面试自检：** “会员到期后视频还能继续播怎么办？App 登录了为什么 WebView 仍是游客？”

## 第 7 步：补 HLS、QoE 与性能

**目标：** 理解播放协议和指标，不把“加载快了”当成结论。

- MP4 是媒体容器，H.264/AAC 是本工程用到的编码；文件扩展名不能保证每台设备都能解码。
- HLS 用播放列表描述分段和不同码率；MSE 是浏览器向媒体缓冲追加数据的接口，二者不是同一层。
- Android/iOS 原生播放由系统/插件内核处理；浏览器侧再按支持情况选择原生 HLS 或 hls.js。
- WebRTC 面向实时音视频，需要信令、ICE、STUN/TURN 等协作；它不是给 video 换个 src 就能完成的直播功能。

当前日志只记“播放器初始化完成耗时”，不是首帧耗时。真正的首帧应以实际画面出现的可观测时刻为准；不同播放器可观测能力不同，要写清测量口径。

建议先做三项指标：

1. 起播成功率：定义发起播放的分母、成功判定和超时窗口。
2. 首帧耗时：从用户播放意图到首个可见画面；区分冷启动、缓存命中和恢复播放。
3. 卡顿：明确播放中 waiting 的起止；排除主动暂停和 seek；统计次数、总时长、比率。

**动手：** 加入一段合法测试 HLS，分别测 Wi-Fi、限速、丢包、切后台。对比单项改动前后 P50/P95，不伪造“提升 30%”。

**验收：** 留下原始事件、统计脚本、样本数和设备环境。手动换 MP4 与 ABR（按网络自动选码率）的区别能讲清楚。

## 第 8 步：补推荐流、弹幕与组件

**目标：** 从单页播放器走向内容产品。

- 推荐流：先实现当前项唯一播放，再做下一项预取；离开项释放资源，不能为每张卡片永久保留控制器。
- 弹幕：评论列表并不等于弹幕。需要媒体时间轴、轨道调度、碰撞策略、seek 重置和开关。
- 评论：补分页、提交中/失败/重试、乐观更新与回滚；当前页面里的评论只用于学习 DOM 交互。
- 组件复用：Flutter 复用 Widget，Web 复用 Vue/React 组件；共享的是数据协议、状态规则和设计约定。

**动手：** 做一个只有 5 条视频的竖屏流，快速滑动 20 次后检查控制器数量、内存和播放声音。

**验收：** 可解释预加载数量如何取舍，为什么只预加载一条不一定总是最好。给出测试数据，不用“无限流很流畅”替代证据。

## 第 9 步：补海外、广告和会员

**目标：** 覆盖加分项，并理解边界。

- 多语言：把硬编码文案迁移到 Flutter ARB 和 H5 翻译资源；同时检查日期、数字、长文本、RTL、字幕语言。当前界面只有中文，顶部英文标签不算国际化。
- 广告：明确正片与广告各自的播放状态、广告结束/失败/跳过后的恢复位置，避免统计把广告时长混进正片。
- 会员/付费：服务端决定资源访问资格；前端处理试看结束、购买返回后的权限刷新和异常反馈。练习先用模拟购买，不接真实付款。
- WebRTC：先做独立双端通话实验，再考虑与直播观看产品组合，不强塞进当前播放器页。

**验收：** 至少完成中英两种语言与一次长文本测试；会员过期不只隐藏 UI；广告失败能恢复正片；明确哪些部分只做了模拟。
